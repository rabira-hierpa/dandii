# Design: Per-operator scoping across the console

Generated by /office-hours on 2026-08-20
Branch: feature/invite-flow-amharic-stops
Repo: rabira-hierpa/dandii
Status: DRAFT
Mode: Startup (intrapreneurship)

## Problem Statement

The invitation workflow grants a `route-operator` a `User.operatorCode`, and
`lib/operator-scope.ts` enforces it. But it only enforces it on the `feedEdit`
family. Everywhere else the scope is decorative.

Observed by the operator of the product: a user invited to Anbessa "can still
access all the route details of the app like an admin."

Two distinct gaps sit behind that report.

**Reads: 0 of 11 console surfaces filter by operator.** Every page and console
API calls `requireRole` or `requirePermission` and then queries the whole
network. `/console/routes` appears to have an operator filter, but it reads
`?operator=` from the URL — a convenience control, not a boundary. An Anbessa
user types `?operator=LRT` and sees LRT.

**Writes: 5 of 6 permission families are unscoped.**

| Family | A route-operator can | Scoped today |
|---|---|---|
| `feedEdit` | edit routes, stops, trips, shapes | yes |
| `fare` | create, update, delete any fare | no |
| `closure` | create, update, delete any closure | no |
| `proposal` | approve/reject any rider fare proposal | no |
| `feed` | generate a full-network GTFS export | no |
| `route` | assign, create, update | partial |

So an Anbessa dispatcher can close an LRT line, delete a Sheger fare, and
approve a rider's fare correction on a route they have never operated. The
report was about visibility; the exposure is larger than visibility.

## Demand Evidence

Not hypothetical. The console is being provisioned for per-operator dispatchers
at five real agencies (Anbessa, Sheger, Alliance, Minibus, LRT) via the
invitation flow shipped in `21ee87c`. The gap was found by using the product,
not by an audit.

The blast radius is rider-facing: a closure or a deleted fare reaches the
published GTFS feed and the public map.

## Status Quo

Nothing prevents it today. `requireRole(CONSOLE_ROLES)` answers "may this person
open the console at all" and stops there. The workaround is trust — a small
enough set of operators that nobody has tried.

That workaround expires the moment the first external dispatcher accepts an
invitation.

## Target User & Narrowest Wedge

**The user:** a dispatcher at Anbessa City Bus, invited as `route-operator`
scoped to `ANBESSA`. They open the console to close a route for a holiday, fix
a stop name, or approve a rider's fare correction on their own line.

**The wedge:** `requireConsoleScope()` plus the two route-owned destructive
families (`fare`, `closure`). That alone removes every action that reaches
riders. Proposal review, feed generation and the nav changes follow in the same
pass but are not what makes it safe.

## Premises

1. **A route's operator assignment is the single source of scope.** Fares,
   closures, proposals, stops and shapes all inherit from the route they belong
   to. No separate ACL. — agreed
2. **A scoped operator sees only their own operator's data.** Not "sees
   everything, edits their own." — agreed (D1)
3. **All five unscoped families get covered**, not just the destructive two.
   — agreed (D2)
4. **Unassigned routes stay admin-only.** Nobody owning a route is not everybody
   owning it. Already the write-side rule; extends to reads.
5. **Analytics and Feed Versions are hidden from route-operators**, not filtered.
   A single-operator "average fare by operator" chart is a different product,
   not a filtered one. — agreed (D4)

**Accepted tradeoff on premise 2.** I recommended "see all, edit only theirs,"
on the argument that a dispatcher planning around a Megenagna closure benefits
from seeing the LRT line that shares the interchange. The user chose full
isolation with domain knowledge of how these agencies actually relate. Recorded
as a deliberate cost, not an oversight: coordination across operators will have
to happen outside the console, and shared-stop edits become invisible rather
than merely refused.

## Approaches Considered

### Approach A: `operatorWhere()` helper at each call site
A shared helper returns the Prisma `where` fragment; every console page and API
spreads it into its own query. Effort M (human ~2d / CC ~30m), risk medium.
Explicit and greppable, smallest diff. Rejected as the primary: forgetting is
exactly how this bug happened — writes were scoped last session and all eleven
reads were missed. A page added in six months defaults to leaking.

### Approach B: `requireConsoleScope()` — scope arrives with the session
Console surfaces stop calling `requireRole` and call `requireConsoleScope()`,
which returns `{ role, operatorCode, routeWhere, canSeeRoute }`. The call that
authorizes the page also hands over the filter. A coverage test walks
`app/console` and `app/api/console` and fails when a surface skips it.
Effort L (human ~4d / CC ~60m), risk low.

### Approach C: Prisma client extension, automatic row-level filtering
Rejected. The same Prisma singleton serves the public rider map, so an
automatic operator filter would either break the public map or need an escape
hatch on every public query — which is Approach A with worse ergonomics and a
debugging story where queries return nothing for invisible reasons.

## Recommended Approach

**B.** The failure mode being reported right now is "a surface was added and
nobody applied the scope." A and C both leave that possible. B turns it into a
red CI run.

Implementation shape:

1. **`requireConsoleScope()` in `lib/session.ts`** — wraps `requireRole`, reads
   `User.operatorCode` from the database (not the session cookie, matching the
   existing write-side rule so revoking a scope takes effect immediately), and
   returns the role plus a ready `routeWhere` fragment.
2. **All 11 read surfaces** adopt it: the 7 console pages, `console/layout.tsx`,
   and the 3 console APIs. `/console/routes` additionally must ignore a
   `?operator=` param that contradicts the viewer's scope rather than trusting it.
3. **Console map** — `/api/geo/routes` currently has no auth because the public
   rider map uses it. Split a `/api/console/geo/routes` that requires a console
   session and applies `routeWhere`; leave the public endpoint untouched.
   Chosen over adding a `scope` param to the shared endpoint because one
   endpoint whose auth depends on who is asking is the ambient-identity trap
   that makes Approach C unsafe. Two endpoints, two obvious contracts.
4. **The remaining write families** get `denyOutOfScope` at the same point in
   each action that `feedEdit` already does: `fares.ts`, `closures.ts`,
   `fare-proposals.ts`, plus removing `feed: ["generate"]` from
   `routeOperatorRole`. Route assignment is already handled and needs no new
   work: `bulkAssignRoutes` refuses scoped users outright, `updateRoute` refuses
   cross-operator reassignment, and `resolveCreateOperator` forces a scoped
   user's own operator onto anything they create. Worth a regression test in
   this pass rather than new enforcement.
5. **Nav** — `sidebar.tsx` drops Analytics and Feed Versions for scoped roles,
   and both routes refuse directly so the nav is not the only gate.
6. **Coverage test** — enumerates the console surface files and asserts each
   imports the scope helper. New page, no helper, red build. Honest limit: an
   import check proves the helper is reachable, not that its `where` was
   actually spread into every query. It catches the whole-file omission that
   caused this bug; it does not catch a half-applied filter, so the per-surface
   assertions in Success Criteria still carry that weight.

7. **Backfill before deploy.** `getUserOperatorCode` already fails closed: a
   `route-operator` with a null `operatorCode` is refused rather than treated
   as network-wide. That is correct for writes and would lock every *existing*
   route-operator out of the console the moment reads adopt the same helper.
   Any `route-operator` row predating `21ee87c` needs an operator assigned, or
   demoting to `user`, as a migration step — not as a support ticket after
   deploy.

## Open Questions

- **Proposal credit.** When a scoped operator approves a fare proposal, the
  submitter earns points. If the review queue is filtered per operator, who
  reviews proposals on unassigned routes? Today nobody would see them.
- **Closures spanning operators.** A road closure physically affects every route
  on that segment. Under full isolation, an Anbessa dispatcher closing a shared
  corridor cannot see the Sheger routes also affected. The existing road-segment
  cascade TODO becomes more important, not less.
- **`/api/console/snap`.** It takes raw coordinates and returns a road-snapped
  line, so it leaks no other operator's data and has no route to scope against.
  It already carries a per-operator throttle. Probably correct as-is, but it is
  the one console API this design does not change, and that should be a decision
  rather than an omission.
- **Does an operator admin tier exist?** Someone at Anbessa who manages several
  Anbessa dispatchers is currently either a network-wide admin or an ordinary
  route-operator. There is no per-operator admin.

## Success Criteria

- A `route-operator` scoped to ANBESSA, signed in, sees only Anbessa routes on
  `/console/routes`, `/console/network`, `/console/fares` and `/console/proposals`.
- `?operator=LRT` on `/console/routes` returns Anbessa routes, not LRT's.
- Every one of the five previously-unscoped write families refuses a
  cross-operator target with a named-owner error, matching the existing
  `feedEdit` behavior.
- Analytics and Feed Versions are absent from the sidebar and refuse direct
  navigation for scoped roles.
- The coverage test fails when a new console page is added without the helper.
- The public rider map still returns all 447 routes.

## Distribution Plan

Existing deployment pipeline covers this — the console ships with the web app
via the dev → main → Coolify path used for v1.3.0.

## Dependencies

- Builds directly on `lib/operator-scope.ts` (`21ee87c`), which supplies
  `getUserOperatorCode`, `denyOutOfScope` and the fail-closed backstop.
- `User.operatorCode` and the migration already exist.
- Should land on top of PR #24, or after it merges, to avoid a third branch
  touching the same console files.

## The Assignment

**Before writing this code: sign in as a real scoped operator and write down
everything you can reach.**

Use `web/scripts/dev-login.ts` to mint a `route-operator` session, set
`operatorCode` to ANBESSA, then walk the console as that user and record every
page, every number, and every button that responds. Two reasons this beats
reasoning from the permission table:

1. The table says what the code intends. The walk says what the product does —
   and the gap between those two is this entire design doc.
2. It gives you the acceptance checklist. Each thing you can reach and should
   not is one line in the coverage test.

Do the walk before the fix, so you have a before to compare against.

## What I noticed about how you think

- You reported this as "they can access all the route details." You framed it
  as a visibility problem, and you were describing the symptom you could see.
  The larger half — that the same user can delete a Sheger fare or approve
  someone else's fare proposal — only showed up when we counted the permission
  families. Your instinct that something was wrong was right before the
  evidence was.
- I recommended "see all, edit only theirs" and you took full isolation
  instead. You didn't argue about it, you just picked the stricter option. On a
  question about what five competing transit agencies should see of each other,
  you have context I don't, and the stricter default is the one you can loosen
  later.
- You said "throughout the console" — not "on the routes page." That phrasing
  is why this doc covers eleven surfaces and a coverage test rather than
  patching the page where you noticed it.
